## 1. 프로젝트를 한 문장으로 이해하기

**사용자가 서비스의 이상 증상을 말하면, 모니터링 정보와 대응 매뉴얼을 조회해 근거가 있는 진단·권장 조치를 제공하는 운영 지원 서비스**를 만든다.

현재 모니터링 정보는 실제 운영 서버가 아닌 샘플 데이터이다. 이번 프로젝트에서 구현할 것은 진단과 대응 안내이며, 서비스 재시작·배포·복구 작업을 자동 실행하는 기능은 포함하지 않는다.

교수님이 강조한 “주어진 내용을 잘 수행하고, 너무 화려하게 하지 않기”를 따른다. 외부 피드백 검토 후에도 개선 5개·추가 4개를 유지하며, 상태 비교는 직전·현재 두 관측만 비교한다. 코드 변경 전 증거는 [전후 비교 증거 체크리스트](BEFORE_AFTER_EVIDENCE.md)를 기준으로 남긴다. 먼저 정확한 대상을 조사하고 필요한 문서를 찾아 사실에 맞게 답하도록 고친다. 이후 결과를 다시 확인하고 비교·저장할 수 있는 기능을 붙인다.

### 실습 코드를 그대로 옮기면 안 되는 부분

- Wave 8의 `mock_validator.py`는 길이만 검사한다. 사실·수치 검증이 구현되어 있는 것으로 취급하지 않는다. 재작성 상한과 피드백 전달 구조를 참고한다.
- Wave 7의 검색·충분성 판정은 준비된 mock 시나리오이다. 자료 개수만으로 이번 진단 근거가 충분하다고 판단하지 않는다.
- Wave 11의 지연은 `asyncio.sleep()`이다. 실습의 시간 단축 수치를 이번 프로젝트 성능으로 발표하지 않는다.
- Wave 12의 `SqliteCheckpointer`는 간단한 자체 저장 클래스이다. LangGraph의 전체 그래프 재개용 체크포인터와 동일한 기능이라고 설명하지 않는다. 예제의 DB 초기화 코드를 일반 기동에 복사하지 않는다.
- Wave 14의 키워드 평가 함수는 키워드 하나라도 포함되면 통과하는 방식이다. 이번에는 조사 범위·문서·수치 연결을 각각 평가한다. 프롬프트 Hub 게시와 공개 공유는 이번 개발 범위에 포함하지 않는다.
- Resource는 항상 정적이라는 일반 규칙으로 확대하지 않는다. 이번 프로젝트에서는 관측을 Tool, 매뉴얼 문서를 Resource로 다루는 기존 계약을 활용한다.

## Phase 0. 기준선과 재현 가능한 테스트 준비

**상태:** 로컬 범위 완료. 외부 LangSmith 추적·유료 OpenAI는 미실행으로 분리 기록. [결과와 실제 검증 범위](PHASE0_RESULT.md).

**목표:** “답변이 나왔다”와 “올바르게 진단했다”를 구분할 기준을 먼저 만든다.

### 개발 작업

1. 현재 소스와 환경 정보를 기준선으로 보존한다. 실행 스크립트의 DB 삭제는 테스트용 임시 DB로만 재현하고 사용자 DB를 삭제하지 않는다.
2. 사진의 8개 시나리오·9개 메시지와 문서의 cache 단독·log 단독 사례를 평가에 포함한다. 이 목록만으로 매뉴얼 6종 전체가 검증되는 것은 아니므로, db-down을 포함한 유형별 고정 fixture를 별도로 만든다. 6종 각각의 선택·비선택 기준을 적고 정상·자료 부족도 검증한다.
3. 모델·모니터링 응답을 고정할 수 있는 테스트 대역을 기존 `SupervisorDeps`로 주입한다. `fake`의 인사 응답을 실제 LLM의 분류 성능으로 평가하지 않는다.
4. 고정 모니터링 스냅샷, 요청 대상, 기대 매뉴얼, 기대 종료 상태를 사례마다 기록한다. 정상·미등록·자료 부족·부분 실패 사례를 분리한다.

## Phase 1. 조사 대상·계획 검증과 대화 연결 — I1, I5 일부

**상태:** 구현·로컬 검사·실제 Ollama 7개 요청·브라우저·재시작 복원 확인 완료. [검증 결과](PHASE1_RESULT.md) · [누적 개발 로그](DEVELOPMENT_LOG.md).

**목표:** 사용자가 말한 서비스와 실제 조사 서비스를 일치시킨다.

### 개발 작업

1. `data/monitoring.json`을 등록 서비스 목록의 기준으로 삼는다. `billing-service` 같은 미등록 이름을 인식하면 다른 서비스로 바꾸지 않는다.
2. 그래프의 계획 실행 전 공통 게이트에서 요청 대상·모델 계획을 대조한다. 기존 어댑터가 미등록 이름을 먼저 auth로 바꾸는 로직도 함께 고친다.
3. 요청한 등록 서비스의 누락은 한 번씩 보완하고, 중복과 요청 범위 밖의 대상은 실행 전에 제외한다. 공통 원인 질문에서도 임의로 전체 서비스를 조회하지 않는다.
4. “로그인이 느려요”처럼 대상이 불명확하면 등록된 서비스 중 무엇을 조사할지 묻는다. 실제로 관리할 별칭을 명시적으로 등록하기 전에는 로그인=auth를 자동 확정하지 않는다.
5. 원래 증상·직전 대상·확인 대기 상태를 저장할 최소 SQLite 세션 맥락을 이 단계에서 추가한다. 사용자가 “auth-service요”라고 답하면 원래 로그인 지연 질문과 합쳐 조사를 이어간다. Phase 5는 이 저장 구조를 재사용한다.
6. `session.db`의 일반 기동 시 삭제를 제거하고 브라우저의 `thread_id`를 로컬 저장소에 유지한다. `GET /sessions/{thread_id}/messages`와 프록시·화면 복원도 이 단계에서 구현한다. POST와 SSE의 기본 대화 저장을 공통화해 v1 SSE의 누락도 보완한다. 새 대화 시작 시에는 별도 ID를 만든다.
7. “그 서비스 다시 확인해줘”는 같은 세션의 직전 조사 대상과 연결한다. 여러 대상을 조사한 뒤 “그 서비스”라고만 하면 다시 확인한다. 새 증상에 맞춰 새로 조회하며 이전 수치를 현재 값으로 사용하지 않는다.
8. 분석 필요 여부의 최종 판단은 `plan`에서 한 번만 한다. `route`는 일반 대화/장애 진단 분류를 맡고 중복된 `needs_analysis` 판단은 제거한다. `gate`는 최종 판단과 작업 목록을 맞춰, 분석 필요가 True이면 analysis 작업을 한 개 보장하고 False이면 제거한다. 앞 단계의 True를 무조건 유지하거나 뒤 단계가 설명 없이 덮어쓰는 구조를 피한다. fake·Ollama·OpenAI의 분류·계획 계약도 함께 맞춘다.

**수정 후보:** `agent/graph.py`, `agent/ollama_llm.py`, `agent/openai_llm.py`, `agent/fake_llm.py`, `agent/session_store.py`, `server.py`, `web_demo_server.py`, `web_chat.html`, 두 `sh/run_agent_*.sh`.

## Phase 3. 조회 실패·시간 초과·스트리밍 오류 처리 — I4

**목표:** 한 작업의 실패가 전체 조사 결과를 지우지 않게 한다.

### 개발 작업

1. 각 MCP 작업을 성공/실패 결과로 감싼 뒤 `asyncio.gather`로 수집한다. 성공 자료와 실패 대상·사유를 모두 다음 노드로 전달한다.
2. 시간 초과·연결 문제 같은 재시도 가능한 오류만 제한적으로 재호출한다. 미등록 대상·입력 오류·없는 문서는 다시 호출하지 않는다.
3. MCP 개별 호출 기한과 요청 전체 기한을 구분한다. 재시도·재작성도 전체 기한 안에서 실행한다.
4. 동기 `httpx.post`로 이벤트 루프를 막는 실제 모델 호출을 비동기로 바꾸고, 그래프 호출부 및 fake 인터페이스도 맞춘다. 기한 도달 시 애플리케이션 작업과 HTTP 스트림을 취소·정리한다. 모델 서버 내부의 추론 중단은 backend 동작을 별도로 확인하며, 클라이언트 취소만으로 추론·과금까지 즉시 중단된다고 보장하지 않는다. MCP 취소 후 공유 세션이 정상 요청을 처리하는지도 확인한다.
5. 답변 생성량 상한을 backend별 요청 옵션에 반영한다. 생성 중단·잘린 응답은 성공한 답변으로 취급하지 않는다.
6. 일부 실패 시 성공 자료 범위의 답변, 전부 실패 시 진단 불가 안내를 반환한다. 추정한 숫자로 빈칸을 메우지 않는다. 실패 격리는 독립적인 조회 작업에 적용하며, 보정할 수 없는 잘못된 계획·실행할 수 없는 입력은 명확히 종료한다. 모든 오류를 무조건 무시하는 구조로 만들지 않는다.
7. SSE에 실패 대상과 사용자 메시지를 담은 이벤트를 전달한다. 화면에서 오류를 표시하고 입력을 복구한다. 정상·실패 경로 모두 종료 상태를 일관되게 표시한다.

**적용한 제한:** 전체 요청 120초, MCP 시도당 10초·최대 2회 호출(재시도 1회), 추가 조사 최대 1라운드, 답변 작성 최대 2회(재작성 1회). 실제 모델 호출당 전체 45초, fast 출력 512토큰·quality 출력 1,024토큰. 제한은 `agent/execution.py`에 모았고 OpenAI·Ollama 요청에 반영했다. 제출 전 실행을 끝낼 수 있도록 정한 초기 정책이며 실제 모델의 성능 측정값이 아니다. 모델이 한도에 걸리면 성공으로 처리하지 않는다.

작성 한도를 적용하면서 강제 합격도 함께 제거했다. 형식 검사 미통과 시 관측만 안내하며, 사실·출처 검증과 초안 상태 표시는 Phase 4에 남는다. [구현·검증 결과](PHASE3_RESULT.md).

**수정 후보:** `agent/graph.py`, `agent/retry.py`, `agent/mcp_client.py`, LLM 어댑터 3종, `server.py`, `web_chat.html`, `web_demo_server.py`의 오류·시간 제한 중계.

**완료 기준**

- [x] payments 성공·cache 실패 시 payments 결과와 cache 실패 안내를 모두 반환한다.

## Phase 4. 근거 검증과 진단 보고서 — I3, F1

**상태: 구현·검증 완료.** [결과·한계](PHASE4_RESULT.md).

**목표:** 사실·추정·조치를 구분하고 검증되지 않은 답변을 합격으로 표시하지 않는다.

### 개발 작업

1. 조사 결과를 근거 ID가 있는 데이터로 정리한다. 관측 근거는 서비스·조회 시각·상태·CPU·메모리·알림·성공 여부를 보관한다. 매뉴얼 근거는 문서 ID·URI·본문·관련 서비스를 보관한다.
2. 보고서를 아래 5개 영역으로 구성한다.

| 영역 | 내용 | 생성 원칙 |
|---|---|---|
| 관측값 | 서비스별 상태·수치·알림·조회 시각 | 수집 데이터에서 코드로 표시 |
| 분석 | 가능한 원인과 근거 | LLM이 작성하되 사실과 추정 구분 |
| 권장 조치 | 확인할 항목과 조건부 대응 | 실제 조회한 매뉴얼 및 관측 근거와 연결 |
| 미확인 사항 | 실패한 조회, 없는 기록, 판단 한계 | 실패·부족 상태를 코드로 반영 |
| 출처 | 관측 근거와 참고 매뉴얼 | 실제 수집 목록에서 코드로 표시 |

3. 자유 형식 문장만 검사하지 않는다. 모델에는 분석·조치와 참조 근거 ID를 구조적으로 받으며 Pydantic 등 기존 도구로 필드를 검증한다. 관측값은 모델이 다시 써서 바꾸지 않게 한다.
4. 시스템·수치의 연결, 없는 출처, 누락 영역, 미조회 대상을 정상으로 단정하는 표현, 조치 조건 누락을 검사한다. 현재 측정 필드와 알림 본문 수치·임계치를 구분한다. 현재 샘플의 알림에는 발생 시각이 없으므로 알림 수치를 임의로 과거 관측이라고 규정하지 않고, 현재 측정값과 차이가 있으면 시점 미확인 한계로 표시한다.
5. “CPU 90% 이상 지속 시 확장”이라는 문서가 있다고 한 번의 조회만으로 지속을 확인했다고 쓰지 않는다. 조건이 미확인되면 조건부 권장 또는 추가 확인으로 표시한다.
6. 실패 피드백에 서비스·필드·기대 근거를 적어 최대 1회 재작성한다. 그래도 실패하면 `unverified`로 종료하고 검증 가능한 관측·출처·한계만 제공한다. 실패한 조치 초안을 단순 경고와 함께 최종 권고로 내보내지 않는다.
7. 검증 전 초안 표시는 스트리밍 설계의 선택으로 다룬다. 이번 기본안은 초안 스트리밍을 유지하되 처음부터 **‘검증 전 초안’**임을 명확히 표시하는 것이다. 반려 시 해당 초안을 최종 답변과 구분하고 재작성 상태를 표시한다. 통과한 결과만 **‘검증 통과’**로 표시하며, 한도 후 실패는 **‘검증 미통과’**로 종료한다. 초안을 숨기고 검증 후에만 표시하는 방식은 대안으로 기록하되, 두 방식을 선택하는 설정 기능은 추가하지 않는다. 이 정책은 장애 진단 답변에 적용한다.
8. POST는 기존 `reply`, `events`, `metadata`를 유지하며 `report`와 검증 상태를 추가한다. SSE는 현재 `FinalAnswer`의 `reply`와 `[DONE]` 종료 형식을 유지하며 보고서·검증 상태를 확장한다. SSE에도 원래 POST와 동일한 metadata 봉투가 있었다고 가정하지 않는다. fake·Ollama·OpenAI의 출력 계약과 화면 처리를 함께 맞춘다.
9. 조사 결과가 분석 모델까지 빠짐없이 전달되게 한다. `analysis_node`에서 사용자 질문과 수집 근거를 함께 넘기고, 각 LLM 어댑터의 `analyze` 입력에 서비스별 CPU·메모리·상태·알림을 포함한다. 메모리 수치를 알림 문장으로 대신하지 않는다. Phase 3에서 정한 비동기 호출 방식에 맞춰 그래프·fake·Ollama·OpenAI의 함수 인자를 함께 수정한다. 미조회 값은 0으로 채우지 않고 미확인으로 전달한다.

**화면·서버 공통 검증 상태**

| 상태 | 의미 | 표시·후속 동작 |
|---|---|---|
| pending | 검증 전 또는 검증 중 | 초안임을 표시하며 합격으로 취급하지 않음 |
| rejected | 이번 초안이 반려됐고 재작성 기회가 남음 | 반려된 초안 구분, 재작성 진행 |
| passed | 정한 검증 기준 통과 | 최종 보고서와 검증 통과 표시 |
| unverified | 검증 실패 후 반복 한도 도달 | 검증 미통과 종료, 확인한 관측·출처·한계만 제공 |

검증 상태는 화면 문장 문자열을 비교해 추측하지 않고 구조화된 값으로 전달한다. `FinalAnswer`는 요청 처리가 끝났다는 뜻이며 항상 `passed`라는 뜻은 아니다. 모델의 원인 추정은 `passed`여도 추정으로 표현한다. 재작성 상한은 유지하고 실패를 합격으로 바꾸는 로직만 제거한다.

## Phase 5. 조사 이력 저장·조회 — F2, I5 마무리

**상태: 구현·검증 완료.** [검사·반영·한계](PHASE5_RESULT.md).

**목표:** 채팅 문자열과 별도로 진단에 사용한 자료와 결과를 다시 확인한다.

### 개발 작업

1. 기존 SQLite를 확장한다. 처음부터 별도 DB 서버를 도입하지 않는다. 기존 `messages`는 유지하고 다음 정도의 저장 구조로 시작한다.

| 저장 항목 | 핵심 필드 | 용도 |
|---|---|---|
| 세션 맥락(Phase 1에서 도입) | thread_id, 직전 대상 목록, 확인 대기 질문, 갱신 시각 | 확인 답변·후속 질문 연결 |
| 조사 기록 | run_id, thread_id, 생성 시각, 종료 상태, 결과 JSON | 관측·문서·실패·검증·보고서 보존 |

2. 조사 기록 JSON에는 시스템별 관측 시각, 데이터 출처/샘플 여부, 성공·실패, 매뉴얼 연결, 검증 상태를 포함한다. 이후 비교를 위해 관측값을 원형으로 저장한다.
3. Phase 1의 공통 저장 흐름에 조사 기록을 추가한다. 조사 run_id는 LangSmith 활성 여부와 무관하게 요청마다 생성하고 LangSmith trace ID와 구분한다. 한 요청의 중복 완료 저장을 막으며 최종 이벤트 전에 저장을 마친다. 별개의 HTTP 재요청까지 자동으로 같은 요청이라고 간주하지 않는다. 완료된 부분 실패·검증 미통과도 상태를 붙여 기록한다. 중간 연결 종료는 작업 취소·정리로 처리하고, 미완성 결과를 완료 기록으로 저장하지 않는다. 중단 요청의 관측은 서버 로그에 남기며 별도 실행 복원 기능은 만들지 않는다.
4. 조회 목록과 상세 API를 만들고 화면에 같은 세션의 이전 조사 목록과 상세 보기를 추가한다. 메시지 복원은 Phase 1에서 만든 API와 화면 동작을 재사용한다.
5. 일반 재시작에서 DB를 초기화하지 않는다. 새 테이블 추가는 기존 데이터가 남는 방식으로 적용한다.
6. 화면에 전송한 초안·반려된 조치를 검증된 최종 보고서로 저장하지 않는다. 최종 보고서와 최종 검증 상태를 함께 저장하고, `unverified` 결과는 확인 가능한 사실과 한계를 담은 별도 종료 상태로 보존한다.

**저장소 선택과 발표 표현:** 단일 서버 로컬 실습에서는 기존 SQLite를 유지해 설치·운영 복잡도를 줄인다. 서버별 별도 DB 파일은 대화를 공유하지 못하며, 같은 DB 파일에는 동시 쓰기 제약이 있다. 실제 다중 서버·쓰기 부하 실험은 수행하지 않았으므로 “락 경합을 확인했다”거나 “실서비스에서는 반드시 Redis로 바꿔야 한다”고 발표하지 않는다. 공유 저장소 전환은 운영 요구가 생겼을 때 검토할 후속 과제다. 현재 자체 메시지 저장소와 LangGraph 체크포인터는 다른 구조이므로 `AsyncPostgresSaver`를 바로 교체 가능한 부품으로 설명하지 않는다. [SQLite 공식 설명](https://www.sqlite.org/whentouse.html), [LangGraph 영속성 설명](https://docs.langchain.com/oss/python/langgraph/persistence).

**API 제안:** Phase 1의 `GET /sessions/{thread_id}/messages`를 재사용하고, `GET /investigations?thread_id=...`, `GET /investigations/{run_id}?thread_id=...`를 추가한다. 프론트 프록시에도 해당 경로를 추가한다. 이는 로컬 실습 범위이며 thread_id 자체를 사용자 인증이라고 설명하지 않는다.

**수정/추가 후보:** `agent/session_store.py`, 필요 시 `agent/investigation_store.py`, `agent/deps.py`, `server.py`, `web_demo_server.py`, `web_chat.html`.

**목표:** 이전 조사 대비 무엇이 달라졌는지 확인하고 보고서를 파일로 저장한다.

### 개발 작업

1. 비교 대상은 현재 조사와 같은 세션·같은 서비스에서, 현재 조사를 제외하고 저장 순서상 가장 최근인 성공 관측 1개로 고정한다. 성공은 모니터링 조회 성공 기준이며 보고서의 검증 상태와 구분한다. 실패·미조회 수치를 0으로 채우지 않는다.
2. 구조화된 숫자 필드로 CPU·메모리의 현재값−이전값을 계산하고 퍼센트포인트(%p)로 표시한다. LLM 답변 문장에서 수치를 파싱하지 않는다. 상태 라벨 변화는 별도로 표시하고, 알림은 문자열 집합 차이로 추가·유지·해소를 구분한다. 문구 변경을 별개의 실제 장애로 확정하지 않는다.
3. 여러 시스템도 서비스별 두 관측만 독립적으로 비교한다. 기록 없음·시각 불명·비교할 숫자 누락·일부 조회 실패는 해당 항목을 비교 불가로 표시한다. 두 관측 시각과 간격을 보여주며, 과거 값을 현재 관측으로 사용하지 않는다.
4. “다시 확인해줘”는 Phase 1의 세션 대상을 이용해 새 조사를 실행한 뒤 비교한다. 변화가 좋아졌다는 이유만으로 복구 완료를 확정하지 않는다.
5. 같은 저장 보고서를 Markdown으로 변환하는 함수를 만든다. 보고서 5개 영역, 검증 상태, 출처, 비교 시각·변화량, 샘플 데이터 안내를 포함한다.
6. 상세 기록에서 다운로드하는 버튼과 API를 추가한다. Markdown 생성에는 LLM을 추가 호출하지 않는다.
7. 내보내기는 최종 저장 보고서를 기준으로 하며 검증 상태를 포함한다. 미통과 결과도 미통과임을 명시하고 반려된 조치를 확정 권고로 내보내지 않는다.

**이번 범위에서 제외:** 여러 시점의 시계열 집계·추세 분석·차트·이상 탐지·알림 의미 분석·장애 재발/복구 완료 판정. “이전 보고서 링크만 제공”으로 F3를 대체하지 않고, 위 두 관측의 숫자·상태·문자열 비교를 최소 구현한다. Markdown 변환뿐 아니라 저장 결과와 다운로드의 일치까지 검증하며 “30분이면 완료” 같은 구현 시간을 보장하지 않는다.

**API 제안:** 비교는 조사 상세에 포함. `GET /investigations/{run_id}/report.md?thread_id=...`에서 해당 저장 기록을 다운로드한다. 프록시에서 다운로드 헤더·내용 형식을 유지한다.

**수정/추가 후보:** `agent/comparison.py`, `agent/report.py`, 저장소 조회 함수, `server.py`, `web_demo_server.py`, `web_chat.html`.

**구현 확정:** 새 조사는 저장 직전에 이전 성공 관측을 조회하여 comparison을 스냅샷으로 함께 저장한다. 같은 단일 서버 이벤트 루프의 동기 저장 흐름이며 다중 쓰기 서버의 직렬성 실험은 하지 않았다. 기존 Phase 5 기록은 조회 시 현재 run_id의 rowid 이전으로 범위를 제한해 읽기 전용으로 계산한다. 시각 누락·역전·동일 시각은 수치 비교를 보류한다. 현재 수업 MCP가 offset 없이 생성한 로컬 시각은 Asia/Seoul로 해석하고 한계를 표시한다. Markdown은 저장된 reply·상태·comparison을 사용하고 조회·내보내기로 새 조사/LLM 호출을 만들지 않는다.

단위 테스트는 결정론적 기준을 모두 통과시키는 것을 목표로 한다. 실제 모델 품질은 반복 결과와 실패 사례를 그대로 기록하고 100%를 전제로 약속하지 않는다. 속도 평가는 같은 설정에서 워밍업을 구분하고 최소 3회씩 측정해 중앙값·범위·실패 건수를 함께 남긴다. 테스트 표본이 작다는 한계도 밝힌다.

LangSmith는 노드·MCP·재작성 흐름을 설명하는 증거로 활용하되, 캡처만으로 보너스나 평가 점수를 보장하지 않는다. 현재 화면은 SSE 경로이므로 POST 추적 성공만으로 판단하지 않고, 실제 SSE 요청에서 같은 요청의 Write → Validate → 재작성/종료가 연결되는지 확인한 뒤 캡처한다. 로컬 고정 평가를 먼저 완성하고 계정·설정·시간이 확보되면 외부 추적·Dataset을 연결한다. 실습 계정·키를 복사하지 않으며 로컬 모델의 가상 비용을 실제 청구액으로 쓰지 않는다.

코드 수정 전에는 [증거 체크리스트](BEFORE_AFTER_EVIDENCE.md)에 따라 현재 원본·입력·fixture·기존 결과를 보존한다. 의도적으로 틀린 초안·조회 실패를 넣은 실험은 “오류 주입”, 실제 Ollama 답변의 실패는 “실모델 관찰”로 구분한다. 현재 평가 코드가 아직 계산하지 않는 지표는 검증기·실패 처리 구현 때 측정 항목을 추가하고 원본과 개선판에 똑같이 적용한다. 현재 fake 4/21 결과나 LangSmith 실행 성공을 실모델 정확도·사실 검증 성공률로 바꿔 발표하지 않는다. 검증 통과율만 높이는 대신 오류 차단과 정답 오차단을 함께 기록한다.

[LangSmith 공식 평가 설명](https://docs.langchain.com/langsmith/evaluation-types)을 참고하며, 외부 피드백의 “무조건 가산점”·“완벽한 아키텍처” 표현이나 원문으로 연결되지 않는 `[지정 오류: ...]` 표시는 발표 근거로 사용하지 않는다.

RAG·LLM-as-judge 등 수업에서 제시한 대안과 달리 선택한 부분은 배경·결정·대안·트레이드오프·재검토 조건을 짧게 기록한다. 모든 버그 수정에 ADR 파일을 만들 필요는 없으며, 이번에는 문서 선택 방식과 검증 방식의 핵심 결정 1~2개를 기록하는 정도로 시작한다. 이는 Capstone의 ADR 학습 내용을 적용하는 제안이며 과제 필수 제출물로 단정하지 않는다.

기존 FastAPI, LangGraph, MCP, Vue 단일 화면, SQLite와 `SupervisorDeps`를 유지한다. 새 노드나 파일은 실제 책임이 생길 때만 추가한다. `graph.py` 전체 분해, 프론트 빌드 도구 전환, DB 서버 교체를 먼저 수행하지 않는다.

필요한 공통 함수는 세 backend가 함께 사용하게 한다. 새 기능은 v2에서 개발하고, v1은 기존 레거시 동작·기본 대화 저장의 호환성을 확인하는 범위로 둔다. `SUPERVISOR_VERSION=v1`을 “개선 전 기준선”이라고 부르지 않는다. 현재 v2 원본과 개선 v2를 같은 조건에서 비교해야 한다.

한 요청의 흐름은 다음과 같다.

> 질문·세션 확인 → 대상 확인 또는 계획 수립 → 계획 검증 → 시스템별 모니터링 → 필요한 매뉴얼 조회 → 부족·실패 정리 → 분석·보고서 작성 → 근거 검증·제한된 재작성 → 저장·최종 제공 → 이력 비교·내보내기

문서 검색·보고서 스키마·실패 표현·저장 데이터를 따로 설계해 서로 다른 값으로 표시하지 않는다. 저장·화면·Markdown은 같은 보고서 데이터를 사용한다.
