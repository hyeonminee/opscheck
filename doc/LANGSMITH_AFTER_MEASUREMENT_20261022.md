# 개선 후 LangSmith 실측 결과

증거: [원시 결과 JSON](../eval/results/langsmith-after-20261022/measurements.json)

측정: 2026-10-22 11:27~11:44 KST · 현재 코드(`chat_request` 루트) · 실제 OpenAI/MCP 실행 · LangSmith API로 **사후 조회만** 했고 모델 호출이나 재측정은 하지 않았다.

**이번 결과에서 확인한 핵심:** 개선 후 후속 질문("그 서비스 다시 확인해줘")은 매번 새 MCP 조회(payments-service 관측 + cpu-spike 매뉴얼)를 수행했다. 복수 서비스 질문은 두 서비스를 모두 조회하고 서비스별 매뉴얼(cpu-spike, memory-leak)을 모두 읽었다. 조회한 11개 요청 모두 오류 span 0건, `processing_status=completed`, `validation_status=passed`였다.

**발표에서 쓰는 개선 후 수치는 세트 B**(11:33:20 단일 3.26초 / 11:33:36 후속 3.39초 / 11:34:11 복수 6.01초, 모두 같은 대화)이며 발표 슬라이드 16·17·20에 이 세트를 쓴다. 이전 초안의 2.95 / 3.05 / 6.01초는 서로 다른 대화 세 개에서 고른 값이라 사용하지 않는다.

## 1. 조회 조건

- 비공개 계정의 LangSmith 프로젝트 `capstone-all-total-openai`에서 2026-10-22 11:00 KST 이후의 루트 `chat_request` 11개를 읽었다. 질문·대화 ID·run 시각은 JSON에 있다. 공개 링크는 만들지 않았다.
- 개선 전과 달리 **측정용 래퍼가 없다.** 개선 전은 `baseline_sse_measurement` 루트와 토큰 계측용 HTTP 스팬을 덧붙였지만, 개선 후는 앱이 원래 만드는 `chat_request` 루트를 그대로 읽었다.
- 이 11개는 사전에 계획한 측정 실험이 아니라 브라우저에서 실행한 요청 기록이다. 모델은 계획·분석 `gpt-4o-mini`, 작성 `gpt-4o`다.
- 요청 시간은 LangSmith 루트의 `end_time - start_time`이다.
- 토큰: LangSmith 기본 토큰·비용 필드는 이 span들에서 0이다. 아래 토큰은 모델 어댑터가 각 LLM span 출력에 기록한 `tokens` 값을 합산한 것이다. 개선 전의 "OpenAI 응답 usage와 LangSmith 루트 집계 일치" 같은 교차 확인은 이번에 하지 못했다. 코드의 가상 비용(`usd`)은 쓰지 않았다.
- 개선 전 문서는 원본 `research`의 0.35초 고정 지연과 첫 Tool 호출의 의도적 Timeout·재시도(`flaky_first_tool_call`)를 유지한다고 적었다. 현재 `agent/graph.py`에는 0.35초 지연 코드가 없다(`baseline/original/agent/graph.py`에만 있음). `mcp_client.py`의 첫 Tool 호출 시뮬레이션은 남아 있다. 조회한 11개 요청에는 오류 span이 없어, 이 시뮬레이션이 어느 요청에서 작동했는지 이 조회로는 확인하지 못했다.

### 이전 초안의 2.95·3.05·6.01초와의 대응(사용하지 않음)

| PPT 수치 | LangSmith에서 찾은 run | 비고 |
|---|---|---|
| 2.95초 단일 | 11:35:14 (대화 D) 2.946초 | 일치 |
| 3.05초 후속 | **11:27:38 (대화 A) 3.047초** | 일치하지만 11:34~11:35가 아닌 11:27 요청 |
| 6.01초 복수 | 11:34:11 (대화 B) 6.013초 | 일치 |

세 수치는 **서로 다른 대화 세 개에서 가져온 값**이다. 같은 대화 안에서 보면 A는 3.476/3.047/6.058초, B는 3.261/3.392/6.013초다. 대화 D의 후속 질문은 4.860초와 3.932초였다. 그래서 "한 번의 단일→후속→복수 측정"으로 표기하려면 한 대화의 세트를 써야 하고, 발표에는 세트 B를 쓴다.

## 3. 사례별 기대와 실제

| 항목 | 기대 | 실제(세트 A·B 모두) | 판정 |
|---|---|---|---|
| 단일 조사 대상 | payments만 조회 | `get_monitoring_status(system_name=payments-service)` 1회 | 충족 |
| 단일 매뉴얼 | CPU 알림 → cpu-spike | `runbook://incident-response/cpu-spike` 조회 | 충족 |
| 후속 질문 | payments 대상으로 새 MCP 조회 | 같은 `get_monitoring_status` + cpu-spike를 새로 조회, 새 수치 | 충족 |
| 복수 조사 대상 | payments/cache 모두 조회 | 두 서비스 모두 `get_monitoring_status` | 충족 |
| 복수 매뉴얼 | cpu-spike + memory-leak | 두 문서 모두 조회 | 충족 |
| 검증 상태 | 구조·수치·출처 검증 | 11개 요청 모두 `passed` | 충족(구조·근거 검사 기준) |

보고서 5개 영역 표시는 이 조회로 직접 확인하지 않았다. 루트 출력에는 상태·검증 값만 있으며 화면 확인은 [최종 평가 검증 보고서](FINAL_EVALUATION_20261022_084843.md)에 있다. 이 표는 세트 A·B 6개 요청의 관측 결과이며 전체 정확도나 실패율로 일반화하지 않는다.

## 4. 개선 전과 비교할 때의 주의

[개선 전 측정](LANGSMITH_BEFORE_MEASUREMENT_20261022_110948.md)과 같은 조건이 아니다.

- 요청 루트: 개선 전은 측정 전용 래퍼 루트, 개선 후는 앱의 `chat_request` 루트. 래퍼 오버헤드는 제거하지 않았다.
- 프로젝트: 개선 전 `opscheck-before-20261022`, 개선 후 `capstone-all-total-openai`. 개선 후는 새로 설계한 실험이 아니라 이미 남아 있는 기록이다.
- 토큰 기록 방식: 개선 전은 OpenAI 응답 usage 합계와 LangSmith 집계가 일치함을 확인했고, 개선 후는 어댑터 기록값만 있다.
- 대화 구성: 개선 전의 복수 요청은 새 대화였고, 세트 A·B의 복수 요청은 같은 대화에서 이어졌다.
- 동적 샘플: 두 실행 모두 MCP 샘플의 임의 변동을 그대로 썼다. 같은 관측을 재생한 실험이 아니다.
- 토큰이 늘었다. 단일 요청 기준 개선 전 922토큰, 개선 후 2,116~2,119토큰이다. 개선 후 write 단계가 서비스별 근거·조치를 구조화 JSON으로 작성하는 만큼 출력이 길어진 것으로 보이지만, 이 조회만으로 원인을 확정하지 않는다. 호출 수도 개선 전 HTTP 호출(3/2/3)과 개선 후 LLM span(2/2/3)이 같은 단위가 아니므로 직접 비교하지 않는다.
- 후속 질문은 개선 전이 재조회를 하지 않아 2.105초였고, 개선 후는 실제로 재조회하므로 3.047~3.392초(세트 A·B)다. 더 느려진 값이 곧 성능 저하는 아니며, 후속 재조회라는 기능 목표를 충족하는 데 든 작업량이다.
- 각 질문 1~2회 관측이라 평균·p95·속도 개선율·비용 절감률을 계산하지 않았다. 청구액은 확인하지 않았다.

## 5. 확인하는 방법

비공개 계정의 LangSmith 프로젝트 `capstone-all-total-openai`에서 루트 `chat_request`를 선택한다. 시작 시각은 2026-10-22 11:27:38 KST(후속 3.047초), 11:34:11 KST(복수 6.013초), 11:35:14 KST(단일 2.946초)이며 트레이스 ID는 JSON에 있다. 하위 `mcp.call_tool`의 `arguments.system_name`, `mcp.read_resource`의 `uri`, `openai_fast.plan`·`openai_quality.write`의 출력 `tokens`로 위 값을 대조할 수 있다. 접근에는 해당 계정의 권한이 필요하며 공개 공유 링크는 만들지 않았다.
