## 검사 결과

- 전체 Python **119개 통과**(기존 Phase 9의114 + 신규5), Node 통과. 고정 검증셋 자동 판정35/35 통과. 4개 후속 계약은 해당 Phase 테스트에서 검사했다.
- **실시간 검증:** cache 작업을 asyncio.Event로 차단한다. 차단을 해제하기 전에 소비자에게 cache running과 payments completed가 도착하고 전체 소비 작업은 아직 종료되지 않았음을 검사한다. 답변 작성도 별도 Event로 차단해 작성 running이 완료 전에 도착함을 검사한다.
- **실제 HTTP 경로:** 임시 loopback uvicorn 백엔드+프록시+HTTPX streaming 소비자로 동일한 차단/도착 조건을 검사했다. FinalAnswer 이후 [DONE], 검증 passed와 저장 snapshot 일치도 확인했다. 최종 이벤트 순서만 확인한 검사가 아니다.
- **실패·회귀:** 타임아웃→두 번째 시도 성공, 다른 대상 영구 실패, 초안 반려→재작성, 미통과 한도, 조건부 분석 생략, 요청 전체 시간 초과, 기존 기록 표시. 기존 취소 미저장 검사는 계속 통과한다.
- **화면 로직:** 동일 ID 중복 행 없음, 시도별 행/단계 수/이벤트 수 분리, 오류 후 입력 가능, 위로 읽는 중 스크롤 유지, 일반/확인 분기 진단 표시 방지.

## 사용자가 직접 확인할 방법

1. 기존 방법으로 백엔드를 재시작하고 화면을 새로고침한다(현재 사용자 서버는 자동 재시작하지 않았다).
2. `payments-service와 cache-service 진단해줘`를 입력한다. 모델이 빠르면 상태가 짧게 보일 수 있다. 느린 작업 도중 도착은 자동 검사로 재현한다.
3. 처리 과정의 시도·반려/최종 검증 상태를 보고 완료 뒤 다시 펼친다.
4. 새 대화 → 조사 이력 → 전체 조사 → 이전 결과 → 저장된 처리 과정과 Markdown을 확인한다.
5. 새 대화의 `그 서비스 다시 확인해줘`는 대상을 물어야 한다.
6. 자동 검사: `.venv/bin/python -B -m unittest discover -s tests -p test_phase10.py -v`, `node tests/test_web_session.cjs`. 네트워크 테스트는 로컬 포트 바인딩 허용이 필요하다. 유료 모델·외부 등록은 사용하지 않는다.

## 한계

인증 없는 개인 실습이며 전체 이력은 같은 DB의 기록을 노출한다. 기존 MCP 세션 Lock은 유지해 실제 연결에 따라 호출 완료가 직렬화될 수 있다. 로컬 HTTP 수신 검증을 모든 배포 프록시/네트워크의 무지연 보장으로 해석하지 않는다. 실모델 품질·가설 의미 전체는 검증하지 않았고 유료 호출0회다. v1은 기존 완료 이벤트 표시를 유지한다. 기존 제출 PPT/ZIP은 이 후속 변경을 포함하도록 다시 생성하지 않았다.
