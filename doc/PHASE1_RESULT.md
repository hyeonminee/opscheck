# Phase 1 결과 — 조사 대상·대화 연결

상태: 구현·로컬 검사·실제 Ollama API·브라우저·재시작 복원 확인 완료(2026-10-21). [누적 개발 로그](DEVELOPMENT_LOG.md).

> 후속 상태: Phase 2의 서비스별 매뉴얼 선택까지 구현·검사했습니다. 최신 상태와 다음 Phase 3 작업은 [Phase 2 결과](PHASE2_RESULT.md)를 참고합니다. 아래 검증 수치는 Phase 1 시점 기록입니다.

## 무엇이 달라졌나

| 상황 | Phase 1 동작 |
|---|---|
| payments 단독 요청 | payments만 조회 |
| payments·cache 요청 | 모델이 누락·중복·추가한 계획을 게이트에서 보정하여 각각 한 번 조회 |
| billing 같은 미등록 이름 | 다른 서비스로 바꾸지 않고 등록 목록과 확인 질문 제공. 혼합 요청도 먼저 확인 |
| “로그인이 느려요” → “auth-service요” | 대상 확인 전 조회하지 않고, 원래 증상과 답한 대상을 합쳐 조사 |
| “그 서비스 다시 확인해줘” | 같은 세션의 직전 대상 하나를 새로 조회. 직전 대상이 여러 개거나 없으면 다시 확인 |
| 이름 소개 | 해당 일반 대화 예시를 장애 조사로 보내지 않음 |
| 새로고침·재기동 | 같은 DB·브라우저 ID로 메시지와 확인 대기·직전 대상 유지 |
| 새 대화 | 별도 ID로 시작. 이전 DB 기록은 삭제하지 않음 |
| 분석 필요 여부 | plan이 결정. gate는 True일 때 분석 작업 1개, False일 때 0개 보장 |

## 검증 결과

- Python 검사 27개: **21개 통과, 기존 결함 6개 예상 실패**. Phase 1 신규 검사 14개 모두 통과.
- 실제 MCP stdio 연결 + fake LLM으로 단일·다중·미등록·미지정 요청 4개 통과. 실제 MCP 호출이며 실제 모델 성능 평가는 아님.
- 임시 SQLite에서 재연결·대화 복원·확인 대기 지속·세션 분리 확인. 기존 사용자 DB를 테스트에 사용하지 않음.
- POST→SSE, SSE→POST 대화 연결, v1 SSE 저장 및 복원 API 확인.
- Node 검사: 메시지 복원·대화 ID 유지·새 대화·중복 제출 차단·DONE 종료. Vue/네트워크 대역을 사용한 로직 검사이며 실제 브라우저 렌더링 검사는 아님.
- Python 8개 파일 구문 검사와 두 실행 스크립트 `bash -n` 통과.
- 원본 `baseline/original/`과 기존 `eval/results/`, `.env`, `session.db`는 변경 대상에서 제외.

실행 명령(프로젝트 루트):

```bash
.venv/bin/python -B -m unittest discover -s tests -v
node tests/test_web_session.cjs
```

남은 예상 실패는 Phase 2의 문서 누락·정상 서비스 기본 문서, Phase 3의 부분 조회 실패, Phase 4의 길이 강제 합격·잘못된 수치·없는 문서 충분성 문제이다. 27개 전부가 기능 합격했다는 의미로 발표하지 않는다.

## 직접 확인할 순서

1. 기존 백엔드를 종료하고 수정된 `bash sh/run_agent_ollma.sh`로 다시 기동한다. 이 스크립트는 DB를 보존하지만 8100 포트 프로세스를 종료하므로 진행 중 요청이 없는 때 수행한다.
2. 프록시 API도 바뀌었으므로 기존 프론트엔드를 종료하고 `bash sh/run_frontend.sh`로 다시 기동한다.
3. `http://localhost:8600`을 새로고침하고 위 표의 질문을 확인한다. 미등록·미지정 질문에서 모니터링 조회가 없는지 본다.
4. “새 대화”에서 이름 소개, 이름 재질문, 화면 새로고침과 서버 재시작 후 재질문을 확인한다.
5. 직전 대상이 한 개일 때 후속 질문은 같은 대상을 새로 조회하고, 두 개일 때는 확인 질문이 나오는지 본다.

이전 버전은 새로고침 전 ID를 저장하지 않았으므로 과거 캡처의 대화를 새 화면과 자동 연결할 수 없다. 새 버전에서 시작한 대화부터 복원한다. 같은 브라우저·같은 origin을 사용한다(localhost와 127.0.0.1은 저장소가 다름). 로그인·권한 관리나 여러 사용자 간 인증 격리는 이번 Phase에 추가하지 않았다.

## 한계와 다음 단계

- 실제 Ollama SSE 대상·대화 연결 7개와 브라우저 미등록·확인 질문·새로고침·서버 재시작·새 대화 분리를 확인했다. 모든 질문의 모델 품질을 보장하지 않으며 이번 기능 확인 시간을 정식 전후 지연 비교로 사용하지 않는다.
- 서비스명 별칭·약칭·상세한 부정 표현은 별도 의미 해석 기능이 아니다. 등록 식별자와 `-service`·번호 형식의 미등록 이름을 검사한다.
- 대화 복원은 메시지 중심이다. 과거 단계 로그·원문 프롬프트와 구조화된 조사 보고서는 Phase 5의 이력 기능과 구분한다.
- 다음은 Phase 2의 시스템별 매뉴얼 선택이다. 초안 표시·강제 합격·부분 실패 처리와 기존 9개 개발 범위는 해당 Phase 계획을 유지한다.

## 후속 보완 — TS-006 이름 역할 혼동

사용자 피드백으로 일반 대화의 역할 혼동을 재검토했다. 역할별 메시지를 두 실제 모델 어댑터에 전달하고, 명확한 이름 소개·재질문은 최근 user 발언에서 직접 확인하도록 보완했다. 모델 자체가 이름을 정확히 답하게 됐다는 의미는 아니다. 최신 검사 36개 중 30개 통과·기존 결함 6개 예상 실패, 기록 기반 API 6개와 브라우저 질문 순서·새로고침을 확인했다. [원인·실패한 시도·코드 발췌·검증·한계](DEVELOPMENT_LOG.md#ts-006--일반-대화에서-사용자와-ai의-이름-혼동)를 참고한다.
