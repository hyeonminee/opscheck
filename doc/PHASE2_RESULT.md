# Phase 2 결과 — 서비스별 대응 매뉴얼 선택

> 이 문서는 Phase 2 완료 당시 기록입니다. 현재 Phase 3에서 실제 조회 예외·시간 제한·강제 합격 제거를 완료했습니다. 최신 상태는 [Phase 3 결과](PHASE3_RESULT.md)를 참고합니다.

완료일: 2026-10-21 · 다음 단계: Phase 3 조회 실패·시간 초과 처리

> **payments의 CPU 문제와 cache의 메모리 문제를 각각의 매뉴얼에 연결했습니다.** 정상 서비스에는 기본 DB 매뉴얼을 붙이지 않으며, 자료 부족과 문서 조회 실패를 구분합니다. 개선 I2의 구현이며 개선 5개·추가 기능 4개 범위는 유지합니다.

## 1. 바뀐 동작

| 상황 | 이전 | Phase 2 |
|---|---|---|
| payments CPU + cache 메모리 | CPU 매뉴얼 하나 | CPU·메모리 매뉴얼을 각 서비스와 연결 |
| gateway 타임아웃 + payments CPU | CPU 매뉴얼 하나 | 네트워크·CPU 매뉴얼을 각 서비스와 연결 |
| web-01 정상인데 사용자는 CPU 급증 주장 | 기본 DB 장애 매뉴얼 | 관측상 정상으로 표시, 문서 선택 없음 |
| 상태 unknown 또는 유효 수치 부족 | 기본 DB 장애 매뉴얼 가능 | 미확인 항목·선택 한계를 남김 |
| 두 서비스가 같은 유형 | 문서·서비스 연결 정보 없음 | 같은 문서는 한 번만 조회하고 두 서비스와 선택 근거를 연결 |
| 문서 없음·빈 문서 | 실패 안내 본문도 성공 자료로 사용 | 성공 근거에서 제외하고 `TaskFailed`·한계 표시 |
| 추가 조사 한도 도달 | 충분으로 강제 전환 | 조사는 종료하되 부족 판정·사유 유지 |

문서에는 `doc_id`, 실제 MCP `uri`, `incident_type`, `related_systems`, `selection_reasons`, `ok`를 붙입니다. 본문은 변경하지 않습니다. 실제 모델 2종과 fake 작성기에 모두 관련 서비스·출처·실패 정보가 전달되도록 연결했습니다.

## 2. 단순하고 명시적인 선택 기준

| 매뉴얼 | 선택 근거 |
|---|---|
| cpu-spike | 유효한 CPU 관측 80% 이상 또는 활성 CPU 알림 |
| memory-leak | 유효한 메모리 관측 90% 이상 또는 메모리 증가·heap·OOM 등 활성 알림 |
| high-latency | 지연·커넥션 풀 활성 알림 |
| network-timeout | timeout·네트워크·패킷 손실 활성 알림 |
| disk-full | 디스크 활성 알림 |
| db-down | database/DB 장애를 명시한 활성 알림. 일반적인 down 상태만으로 선택하지 않음 |

CPU 80%는 샘플 모니터링의 경고 기준, 메모리 90%는 제공 런북의 위험 수준을 참고한 **문서 선택 기준**입니다. 원인 확정이나 조치 실행 조건을 뜻하지 않습니다. 메모리 사용률만으로 누수를 확정하거나 CPU 한 번 관측으로 지속 상태를 확정하지 않습니다. 정상 상태·낮은 수치·알림 없음이면 문서를 선택하지 않습니다. unknown·매칭되지 않는 성능 저하·누락/범위 밖/문자열/NaN 수치는 정상으로 대체하지 않습니다.

기존 6종 문서와 활성 알림 표현에 맞춘 규칙입니다. BM25·임베딩·벡터 DB는 도입하지 않았으며, 이를 임베딩 RAG 구현으로 발표하지 않습니다.

## 4. 검증 결과

- 수정 전 새 검사 10개에서 실패 6개·오류 4개를 재현했습니다. 누락된 새 모듈·메타데이터와 기존 잘못된 동작을 확인한 것입니다.
- 수정 후 전체 Python 검사 **47개 중 44개 통과·기존 결함 3개 예상 실패**. Phase 2 검사 11개 모두 통과했습니다.
- 6종 매뉴얼의 선택·비선택, CPU/메모리 경계, 잘못된 수치, unknown, 문서 중복 조회 방지·추가 조사 한도·한도 후 부족 유지·정상 판단을 고정 자료로 확인했습니다.
- HTTP 대역으로 OpenAI·Ollama 작성 프롬프트에 관련 서비스·출처·실패가 전달되는지 검사했습니다. 실제 LLM 답변 품질 검사와 구분합니다.
- **실제 MCP stdio 2개 서버 + fake 모델**로 CPU+메모리, 네트워크+CPU, 정상, 실제 Resource 파일 누락의 4개 사례를 확인했습니다. 사용자 원본 문서는 건드리지 않고 임시 복사본에서만 누락시켰습니다.
- 별도 임시 포트의 브라우저에서 두 서비스의 선택·매뉴얼 조회·최종 답변·전송 버튼 복구를 확인했습니다. Node 화면 로직 검사도 통과했습니다.
- 실제 8100 OpenAI 백엔드에 코드를 반영·정상 재기동했습니다. 8600 프록시 health와 새 HTML 응답을 확인하고, 기존 메시지 **120개 내용·순서를 보존**했습니다. 이번 Phase의 유료 모델 호출은 0회입니다.

### 같은 고정 입력의 전후 비교

비교 대상은 **Phase 1 코드와 Phase 2 코드**이며 같은 21개 질문·관측 fixture·fake 모델을 사용했습니다. 이는 실제 모델 정확도나 응답 속도 비교가 아닙니다.

| 고정 사례 | Phase 1 | Phase 2 |
|---|---|---|
| payments+cache의 필수 매뉴얼 포함 | 1/2개 | 2/2개 |
| gateway+payments의 필수 매뉴얼 포함 | 1/2개 | 2/2개 |
| 정상 web의 불필요한 DB 매뉴얼 | 1개 | 0개 |
| unknown 관측의 불필요한 DB 매뉴얼 | 1개 | 0개 |
| Not Found 본문의 성공 문서 처리 | 있음 | 없음 |

동결 평가의 전체 조건은 13/21 → 17/21입니다. 남은 4개 중 2개는 Phase 0 기대 route=incident와 Phase 1의 올바른 확인 질문 route=clarify가 다른 사례이며, 1개는 후속 Phase의 실제 조회 예외 문제, 1개는 일부러 없는 문서의 필수 문서 포함 조건입니다. **이 수치를 종합 진단 정확도라고 쓰지 않습니다.** 기존 `eval/results/`는 덮어쓰지 않고 이번 결과를 별도 개발 로그에 보관했습니다. 인위적 작업 지연이 있어 성능 향상을 주장하지 않습니다.
