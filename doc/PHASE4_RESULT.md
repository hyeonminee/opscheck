## 1. 이제 보고서는 다섯 영역으로 나옵니다

| 영역 | 무엇이 들어가나 | 만드는 방법 |
|---|---|---|
| 관측값 | 서비스·상태·CPU·메모리·조회 시각·알림 | 실제 수집 값에서 코드로 표시 |
| 분석 | 미확정 가설 + 서비스별 측정 주장과 근거 ID | 모델 JSON을 코드로 검사 |
| 권장 조치 | 실제 매뉴얼의 단계·조건·연결 출처 | 모델이 단계 선택, 코드는 원문과 미확인 조건 표시 |
| 미확인 사항 | 조회 실패·누락 수치·단일 관측·알림 시점 한계 | 수집 상태에서 코드로 생성 |
| 출처 | obs:서비스, doc:장애유형 ID와 실제 Tool/URI | 성공 수집 목록에서 코드로 생성 |

보고서의 관측값과 출처를 모델이 다시 작성하지 않게 했습니다. 모델은 분석 가설과 `field/value/evidence_id` 측정 주장, 매뉴얼 근거 ID·단계 번호를 JSON으로 반환합니다. Pydantic은 필수 항목·타입·추가 필드를 검사하고, 코드가 실제 관측·문서와 대조합니다.

예를 들어 `obs:payments-service`의 CPU가 91이면 `cpu_percent=1`은 반려됩니다. 자유 가설 문장에는 숫자를 쓰지 않고 수치는 구조화 주장에만 넣습니다. 이 제한은 수치가 자유 문장으로 우회하는 것을 줄이기 위한 보수적인 설계입니다.

## 2. 검사하는 것과 실패 시 동작

| 검사 | 차단하는 예 |
|---|---|
| 서비스·관측 연결 | gateway의 관측을 payments의 근거로 사용 |
| 필드·측정값 | CPU 91을 1로 변경, 문서의 90% 임계치를 현재 관측으로 사용 |
| 상태·미조회 대상 | 실패/unknown 서비스를 정상으로 진단, unknown의 기본 0을 측정값으로 제시 |
| 출처·문서 단계 | 없는 문서 ID, 다른 서비스에 연결된 문서, 없는 단계 번호 |
| 조치 조건 | 단일 관측으로 조건·지속 여부를 확인했다고 선언 |
| 보고서 계약 | 필수 영역·주장 누락, 알 수 없는 측정 필드, 잘못된 타입 |
| 반복 한도 | 최초 작성 + 재작성 1회. 다시 실패하면 unverified 종료 |

조치 본문을 모델이 자유롭게 바꾸지 않게 했습니다. 실제 조회한 문서의 선택된 단계 문장을 그대로 사용하므로 “CPU가 90%를 넘고 지속되면” 같은 조건을 없애지 않습니다. 모든 조치는 **조건·지속 여부 미확인, 해당 조건 확인 후 검토**로 표시합니다. 현재 값이 임계치보다 낮아도 문서의 조건부 절차를 참고로 보여줄 수 있으며, 조건을 이미 충족했다고 판단하거나 실제 조치를 실행하지 않습니다.

검증 실패 피드백에는 서비스·필드·기대값·근거 ID를 남깁니다. 한도 후에도 실패하면 **분석 가설과 권장 조치는 최종 보고서에서 제외**하고 관측·출처·한계만 제공합니다. 전체 조회 실패나 실행 기한 초과도 같은 5개 영역 형식으로 안내합니다.

단일 관측의 측정값과 활성 알림 본문을 구분했습니다. 알림에 CPU 91%, 현재 측정에 CPU 89.3%가 있으면 두 값을 각각의 영역으로 표시합니다. 제공 데이터에는 알림 발생 시각이 없으므로 알림을 과거 관측으로 단정하지 않습니다.

## 3. 화면과 API

| 상태 | 화면 표시 |
|---|---|
| pending | 검증 전 초안 |
| rejected | 반려된 초안·최종 답변 아님 + 사유 |
| passed | 검증 통과 + 5개 영역 보고서 |
| unverified | 검증 미통과 + 확인한 자료만 안내 |

모델 JSON 원문 대신 가설 문장이 완성될 때 초안으로 중계합니다. 첫 표시부터 pending 상태를 붙이고 반려된 초안은 별도로 남깁니다. 일반 대화·이름 기억에는 검증 배지를 붙이지 않습니다. OpenAI는 제공자 응답을 완성한 후 가설 문장을 중계하므로 제공자 토큰 스트리밍을 새로 구현한 것으로 발표하지 않습니다.

POST는 기존 `reply/events/metadata`를 유지하고 `report`를 추가합니다. SSE는 기존 `FinalAnswer.reply`·`[DONE]`을 유지하며 `report`·`validation_status`를 추가합니다. 일반 대화의 report는 null입니다. 최종 문자열은 기존 SQLite 대화 저장 경로를 유지합니다. **구조화 report를 조사 이력으로 저장하는 작업은 Phase 5**입니다.

## 4. 검증 결과

- 수정 전: Python 65개 중 64개 통과·수치 검증 1개 예상 실패.
- 수정 후: **Python 80개 모두 통과**, 예상 실패 0개. 새 Phase 4 검사 15개와 기존 CPU 오류 검사를 포함합니다.
- Node: 초안·반려·통과 상태, 최종 report 연결, 일반 대화 배지 제외, 이전 세션·오류 후 재입력 검사 통과.
- 실제 MCP stdio + fake 모델: 복합 CPU/메모리, 네트워크/CPU, 정상 서비스, 두 번 검증 실패의 4개 API 사례와 SSE pending→rejected→passed 확인.
- 임시 브라우저: 반려 상태·검증 통과 보고서·한도 후 미통과 보고서·보내기 버튼 복구 확인.
- 분석 모델 입력: 질문·서비스·메모리 88.8%를 fake 그래프와 OpenAI/Ollama HTTP 대역에서 확인. 입력 전달과 모델 분석 품질은 구분합니다.
- 깨진 JSON 초안도 미리보기에서 전체 요청을 중단하지 않고 검증·재작성 경로로 보냅니다.

### 실제 OpenAI 작성 모델에서 발견한 문제

고정 관측 + fake fast 모델 + 실제 gpt-4o 작성 모델로 두 서비스 진단을 확인했습니다. 최초 두 작성에서 `document_id`에 `cpu-spike.md` 파일명을 넣어 미통과했습니다. 코드가 잘못된 조치를 최종 결과에서 제외했습니다.

문서 파일명과 `doc:cpu-spike` 근거 ID를 구분하도록 필드 설명·작성 지침·피드백을 보완한 뒤, **같은 고정 진단이 첫 작성에 통과**했습니다. 총 실제 작성 호출 3회·사용 토큰 합계 7,746이며 실제 청구 금액은 확인하지 않았습니다. 최초 실패와 보완 후 결과를 모두 보존했습니다. 이는 작성 계약의 작은 검증이며 전체 파이프라인·실모델 종합 정확도 점수가 아닙니다.

### 전후 비교를 읽는 방법

동일한 자유형 CPU 1% 오류 답변은 Phase 3에서는 길이·번호를 충족해 통과했지만 Phase 4에서는 구조화 계약부터 반려됩니다. 별도 Phase 4 검사는 **올바른 JSON 안의 수치·필드·근거 ID를 변조**해서 차단 여부를 검사합니다. 이 둘을 혼동해 자유형 입력 비교가 수치 검증 정확도 실험이라고 발표하지 않습니다. 속도·100% 의미 정확도 향상도 주장하지 않습니다.

## 6. 직접 확인할 것과 남은 작업

[채팅 화면](http://localhost:8600)을 **새로고침**한 후 아래 중 하나를 입력합니다. 현재 OpenAI 모드이므로 새 진단에는 API 호출이 발생합니다.

1. `payments-service와 cache-service 장애 진단` → 두 서비스의 관측·문서 출처와 5개 영역 확인.
2. `cache-service 메모리를 비교해줘` → 메모리 관측과 분석·미확인 한계 확인.
3. `web-01 CPU 급증 원인을 확인해줘` → 실제 관측이 정상이라면 불필요한 장애 문서·조치 없이 보고서 제공.

미통과 강제 시나리오는 실제 서버의 숨은 명령으로 만들지 않았습니다. 개발 로그의 임시 runner와 자동 검사에서만 오류를 주입합니다.

```bash
.venv/bin/python -B -m unittest discover -s tests -v
node tests/test_web_session.cjs
```

- 가설 문장의 의미 전체를 판정하는 검증은 아닙니다. 일부 단정 표현 검사도 제한된 규칙입니다. 정당한 자유 문장을 보수적으로 반려할 수 있으며 수치 설명은 typed claims로 표현해야 합니다.
- Ollama의 실제 생성 품질은 이번 단계에서 재측정하지 않았습니다. 입력·출력·시간 제한 계약은 대역으로 검사했습니다.
- 실제 운영 데이터·장기 변화·복구 효과·조치 실행 검증은 아닙니다. 자료는 수업 샘플입니다.
