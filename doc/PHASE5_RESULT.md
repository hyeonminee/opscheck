## 2. 저장 구조와 처리 기준

기존 `session.db`에 `investigations` 테이블과 세션 검색 인덱스를 추가했습니다. `messages`, `session_context`는 유지합니다. 별도 DB 서버·패키지는 추가하지 않았습니다.

| 저장 항목 | 내용 |
|---|---|
| 식별·질문 | UUID run_id, thread_id, 원래 질문, 맥락을 반영한 질문, 조사 대상 |
| 시각·데이터 표시 | 저장 완료 시각(UTC), is_sample, MCP Tool/Resource 샘플 안내 |
| 원형 자료 | 관측 수치·조회 시각·알림·문서·서비스 연결·실패·문서 선택 한계 |
| 결과 | 최종 5개 영역 report, reply, 처리 상태, 검증 상태, 검증 이벤트 |
| 추적 | 별도 langsmith_run_id. 추적을 꺼도 run_id 생성 |

POST와 SSE가 같은 저장 함수를 사용하고 **메시지·맥락·조사 기록을 한 트랜잭션으로 커밋**합니다. SSE는 `FinalAnswer`를 보내기 전에 저장을 마칩니다. 같은 run_id의 중복 완료 호출은 메시지·이력을 중복 저장하지 않습니다. 별개의 HTTP 재요청은 새 UUID를 가진 별도 조사입니다.

- 일반 대화·대상 확인 질문은 대화에만 남기고 조사 이력에서는 제외합니다.
- 정상·부분 실패·검증 미통과·시간 초과로 종료된 조사는 각각의 상태로 저장합니다.
- 처리 중 취소된 요청은 완료 메시지·조사 이력으로 남기지 않고 확보한 샘플 관측만 서버 로그에 기록합니다.
- 초안 본문·최종 프롬프트·검증되지 않은 분석 노드 요약은 새 조사 이력에 넣지 않습니다. 검증 실패 사유 이벤트는 남깁니다.
- 미통과 report에는 실패한 가설·조치가 없으며 관측·출처·한계만 저장합니다.

## 3. 화면과 API

화면 상단 **조사 이력**을 누르면 현재 대화의 최근 20건이 나옵니다. 기록을 누르면 저장된 보고서·저장 시각·검증 상태를 확인합니다. “현재 상태를 새로 조회한 결과가 아니다”라는 샘플 안내를 표시합니다. 목록·상세의 저장 시각은 한국 시간으로 표시합니다.

| API | 결과 |
|---|---|
| `GET /investigations?thread_id=...&limit=20` | 같은 세션의 최신순 목록, limit 1~100 |
| `GET /investigations/{run_id}?thread_id=...` | 저장된 상세. 다른 세션·없는 ID는 404 |
| POST `/chat` 응답 `metadata.run_id` | 서버가 생성한 요청 UUID |
| SSE `FinalAnswer.run_id` | 같은 요청의 저장 기록 ID |

조회 요청은 MCP·모델을 호출하지 않습니다. 새 대화로 전환한 뒤 도착한 이전 세션 응답이나, 다른 기록을 선택한 뒤 늦게 도착한 이전 상세 응답이 현재 화면을 덮지 않도록 확인했습니다. `thread_id` 필터는 세션 구분이며 사용자 인증은 아닙니다.

## 4. 검증 결과

- 수정 전 Python 80개 통과 → 수정 후 **92개 모두 통과**. 신규 Phase 5 검사 12개입니다.
- 기존 스키마 마이그레이션에서 이전 메시지·맥락 보존, DB 재연결 후 보고서 복원 확인.
- 중복 완료 방지, 메시지·기록·맥락 저장 중 오류 발생 시 트랜잭션 롤백 확인.
- POST/SSE 저장 기준, 완료 이벤트 전 저장, 다른 HTTP 요청의 새 UUID, 부분 실패·미통과·시간 초과 기록 확인.
- POST/SSE 중간 취소 시 미완료 이력 제외와 확보 관측의 서버 로그 확인.
- 세션별 목록·상세 분리, 잘못된 limit, 다른 세션의 상세 404, 프록시·연결 오류 처리 확인.
- Node 검사: 목록·상세·새 대화 초기화·오래된 응답 무시·이력 조회 오류 표시와 기존 채팅 동작 통과.
- 실제 MCP stdio + fake API로 POST/SSE·미통과 이력 3건을 저장하고 일반 대화는 제외했습니다.
- 임시 백엔드를 **실제로 재시작**한 뒤 이력 3건·대화 8개와 상세 보고서 내용이 그대로 유지됐습니다. 브라우저에서도 새로고침 후 같은 기록을 다시 열었습니다.
- 이번 Phase의 유료 모델 호출은 **0회**입니다. 실제 OpenAI 서버는 기존 모델 설정을 유지하며 이력 기능의 검증은 격리된 fake 환경에서 수행했습니다.

실제 8100·8600 서버를 정상 재기동하고 OpenAI 설정을 유지했습니다. 기존 메시지 130개·세션 맥락 13개를 보존했으며 조사 테이블은 초기 0건으로 생성했습니다. 반영된 코드에서도 Python 92개·Node 검사를 통과했습니다. 백업·재기동 상세는 `dev_logs/20261021-phase5/status.json`에 기록했습니다. 기존 메시지 본문과 환경 파일 원문·키는 개발 로그에 복사하지 않았습니다.

원시 근거는 같은 폴더의 `before-tests.log`, `tests.log`, `ui-tests.log`, `mcp-smoke.json`, `restart-smoke.json`, `browser-phase5.txt/png`, `review.diff`, `status.json`입니다. 이전 소스·문서는 `before/`에 보존했습니다.

## 6. 직접 확인하기와 남은 작업

1. [채팅 화면](http://localhost:8600)을 새로고침합니다.
2. `payments-service 장애 진단`을 입력합니다.
3. 상단 **조사 이력** → 방금 조사한 기록을 누릅니다.
4. 새로고침 후 다시 열어 수치·출처·검증 상태가 유지되는지 확인합니다.
5. **새 대화**를 누르면 이전 기록을 지우지 않고 새 세션의 빈 목록으로 전환합니다.

실제 서버의 새 진단은 현재 OpenAI 모델을 사용합니다. 저장된 이력의 단순 조회는 새 모델 호출 없이 처리합니다.

```bash
.venv/bin/python -B -m unittest discover -s tests -v
node tests/test_web_session.cjs
```

이력은 같은 로컬 DB 파일·세션에서 복원됩니다. 여러 서버의 DB 공유, 인증·권한, 자동 삭제 정책, 대규모 동시 쓰기 부하는 구현·측정하지 않았습니다. 서버가 저장을 완료한 뒤 클라이언트가 연결을 끊으면 완료 기록은 남을 수 있습니다. 네트워크 전달 확인까지 포함한 중복 방지 기능은 아닙니다.
