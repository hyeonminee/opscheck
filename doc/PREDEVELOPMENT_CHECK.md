환경을 준비한 뒤의 실행 흐름:

```text
프로젝트 루트에서 최초 준비
  1. bash sh/setup_venv.sh
  2. bash sh/setup_ollama.sh
        ↓
터미널 A: bash sh/run_agent_ollma.sh
        ↓ 8100 /health 확인
터미널 B: bash sh/run_frontend.sh
        ↓
브라우저: http://localhost:8600
```

`.env`는 백엔드를 켜기 전에 준비해야 합니다. OpenAI는 `run_agent_openai.sh`를 **3-1 대신** 사용하며, OpenAI만 쓰면 Ollama 준비는 필요 없습니다. 현재 기동 스크립트에 DB 삭제·포트 프로세스 종료가 있으므로 아래 조건을 먼저 확인합니다.

## 2. 현재 폴더의 실행 준비 상태

| 항목 | 확인 결과 | 다음 작업 |
|---|---|---|
| `.venv` | 없음 | 프로젝트 전용 가상환경·의존성 설치 |
| `.env.example` | 없음 | Phase 0에서 비밀 값 없는 템플릿 작성. 현재 `cp .env.example .env`는 불가 |
| `.env` | 없음 | 선택 backend·모델·추적 여부를 로컬 설정. 키를 문서에 기록하지 않기 |
| 기본 fast 모델 `qwen3:0.6b` | 로컬 기본 저장 경로에 설치 manifest 없음 | 사용할 모델 확정 후 준비. 별도 모델 저장 경로·다른 Ollama 서버는 미확인 |
| `qwen3:8b` | 기본 저장 경로에 manifest 있음 | 설치 흔적만 확인. 이번에는 추론 가능 여부를 검사하지 않음 |
| 모델 설정 순서 | 두 기동 스크립트가 `.env`보다 먼저 표시용 모델을 결정 | Phase 0에서 로딩 순서 수정. 특히 Ollama 검사·웜업·서버 모델 일치 확인 |
| Ollama 준비 | `.env`를 읽지 않음. 기본은 모델 재사용 | 모델 변경은 셸 환경변수로 전달. 강제 새 다운로드는 `OLLAMA_FORCE_REFRESH=1`일 때만 |
| DB와 프로세스 | 두 백엔드 스크립트가 8100 프로세스 종료·DB 삭제. frontend는 8600 종료. 모델 준비는 기존 11434 종료 | 기존 대화·다른 작업에 영향 확인. 일반 기동 DB 삭제 제거는 Phase 1 |
| `sh/run.sh`, `eval/`, `tests/` | 없음 | 없는 실행 파일을 안내하지 않기. 평가·테스트는 계획에 따라 추가 |

**따라서 명령 순서가 맞다는 것과 지금 바로 정상 실행된다는 것은 다릅니다.** 설치와 모델 준비는 이번 문서 검증에서 수행하지 않았습니다.

## 4. 이번에 실제로 확인한 범위

프로젝트를 임시 폴더로 복사하고 기존 임시 가상환경에서 실행했습니다. `.env`와 외부 추적을 사용하지 않았으며, 모델은 fake입니다. MCP 서버 두 개는 실제 stdio 자식 프로세스로 연결했습니다.

| 검사 | 결과·의미 |
|---|---|
| Python 14개, 셸 6개 문법 | 통과. 의존성 전체 호환성·실제 모델 품질까지 보장하지 않음 |
| `.env` 없는 backend 기동 | 복사본의 두 스크립트 모두 안내 후 종료 코드 1. DB 삭제·포트 종료 단계 전에 차단됨 |
| 백엔드 없는 frontend 기동 | curl 실패 대역을 넣은 복사본에서 안내 후 종료 확인. 실제 포트 프로세스에는 접근하지 않음 |
| `/health` | fake/v2로 정상 응답. 같은 수명주기에서 객체 ID 동일, 생성 1회 |
| 장애 POST | “auth-service 응답 지연 장애 진단해줘” 처리 완료. 추가 조사 1회·재시도 1회·작성/검증 2회 관찰 |
| SSE 일반 대화 | RouteDecided → AnswerToken → Finalize → FinalAnswer, 마지막 `[DONE]` 확인 |
| 같은 DB·ID 유지 | TestClient 수명주기를 닫고 다시 연 뒤 “민수” 기억 확인. 별도 OS 프로세스 재시작이나 원본 기동 스크립트 검증은 아님 |
| 프론트엔드 HTML | `/` 응답 200 및 Vue 코드 존재 확인. 실제 브라우저 렌더링·8100↔8600 프록시 통합은 미확인 |
| fake 분류 한계 | “auth-service 응답이 느려요”는 chat으로 분류됨. 정규식에 없는 표현을 실제 모델의 분류 실패와 혼동하지 않기 |
| 원본 보존 | 코드·셸·JSON·HTML 해시 비교로 변경 없음 확인. 변경 대상은 문서와 대시보드 |

테스트 스크립트·원시 결과·수정 전 문서 백업은 임시 폴더에 있습니다. 임시 경로이므로 장기 보관 자료로 간주하지 않습니다. 기능별 정상/실패 시나리오와 수치는 Phase 0의 정식 기준선에서 다시 고정해야 합니다.

**이번에 하지 않은 것:** 원본 기동·설치 스크립트의 전체 실행, 모델 다운로드, 실제 Ollama/OpenAI 추론, LangSmith 외부 기록, 브라우저 화면 시연, 개선 후 품질·성능 측정. PDF의 예시는 점검 자료로 사용했으며 실행 명령으로 자동 수행하지 않았습니다.

## 5. 개발을 시작할 순서

1. **Phase 0:** 설정 템플릿·가상환경·모델 준비, `.env` 로딩 순서 수정, 현재 v2 원본과 고정 테스트 보존. 실제 모델 요청과 브라우저 연결 확인.
2. **Phase 1~4:** 대상·맥락 연결 → 서비스별 매뉴얼 → 실패 처리 → 근거 검증·보고서. 현재 수집·분석·검증 연결 문제를 이 단계 안에서 고침.
3. **Phase 5~6:** 같은 보고서와 상태를 저장해 이력·비교·Markdown 내보내기로 연결.
4. **Phase 7:** 같은 입력·데이터·모델 조건으로 전후 평가. 한계와 미확인 항목을 발표에 포함.

계획의 세부 항목은 아직 구현 전입니다. 개발 단계의 순서를 바꾸거나 기능 개수를 늘릴 필요는 없으며, **환경 준비와 기준선 검증부터 시작하는 것이 맞습니다.** 실제 제출 날짜와 작업 가능 시간은 별도 확인이 필요합니다.
