# 회귀 테스트용 쿼리 — 베이스라인 관찰과 개선 후 기준

> 아래 표의 세 번째 열은 제공된 베이스 코드의 의도·관찰 항목입니다. 모든 backend에서 통과했다고 확인한 결과가 아니며, auth 자동 대체를 개선 후 정답으로 채택한다는 뜻도 아닙니다.
>
> PDF 물리적 9쪽(인쇄 슬라이드 8)의 8개 시나리오·9개 메시지에 cache 단독·log 단독을 추가한 10개 시나리오·11개 메시지입니다.

|---|---|---|

## 개선 후에는 무엇을 기대하나요?

| 사례 | 개선 후 합격 기준 — 아직 미구현 |
|---|---|
| 1~3 단독 요청 | 요청한 서비스만 조회하고 해당 증상의 매뉴얼 연결 |
| 4~6 복수 요청 | 요청한 서비스를 누락 없이 조회. 서비스별 매뉴얼 연결. 공통 원인 분석은 가설·근거·한계를 구분 |
| 7 대상 없는 요청 | auth로 단정하지 않고 조사 대상을 확인한 뒤 원래 증상으로 조사 진행 |
| 8 미등록 서비스 | billing을 auth로 대체하지 않고 미등록 안내. 확인 전 임의 조회 금지 |
| 9 일반 대화 | 장애 조사 없이 답변. 이벤트 수신과 최종 종료를 별도로 확인 |
| 10 이름 기억 | 두 메시지에 같은 `thread_id` 사용. DB를 보존한 재시작과 페이지 복원도 별도 검사 |

## 실행·측정 조건

- 실행 준비는 [README](README.md), 현황은 [개발 전 점검](PREDEVELOPMENT_CHECK.md) 참조.
- fake는 규칙 기반 테스트 대역이다. “느려요”·“타임아웃” 등의 표현이 장애 키워드 정규식에 걸리지 않으면 chat으로 처리한다. 따라서 사진 질문의 실제 모델 성능을 fake 결과로 대신하지 않는다.
- 모니터링 수치는 임의 변동하므로 전후 비교에는 고정 fixture가 필요하다. 모델명·추론 설정·입력·반복 횟수를 기록한다.
- 현재 기동 스크립트는 DB를 삭제하고 페이지 새로고침은 ID를 바꾼다. 재시작 기억을 검증하려면 DB 보존과 같은 ID를 별도로 확보해야 한다. v1 SSE 저장 누락도 구분한다.
- 기존 표만으로 매뉴얼 6종이 모두 검증되지 않는다. db-down을 포함한 유형별 선택·비선택, 정상·자료 부족·부분 실패·검증 미통과 사례는 Phase 0에서 `eval/cases.json`과 `tests/`에 보강했다. 실제 모델 품질 검증과 구분한다.

Phase 0에서 21개 고정 시나리오와 회귀 검사를 추가했다. [실행 명령·결과·한계](PHASE0_RESULT.md)를 기준으로 원본과 현재를 비교한다.

## 코드 변경 전 증거와 비교 기준

- [전후 비교 증거 체크리스트](BEFORE_AFTER_EVIDENCE.md)를 기준으로 기존 노션 캡처의 질문·실제 대상·문제점을 한 줄씩 연결한다. 이미 남긴 화면을 모두 다시 촬영하지 않는다.
- 원본 소스·고정 입력·fixture·현재 JSON과 검사 로그는 보존한다. 재실행이 필요하면 다른 출력 파일명을 써서 기존 결과를 덮어쓰지 않는다.
- 미등록·대상 확인·후속 질문과 재시작/새로고침은 각각 기록한다. 후속 질문은 바로 앞의 단일 서비스 질문과 같은 대화로 이어간다. 화면 유지와 실제 서버 기억은 구분한다.
- 검증은 오류 초안 차단과 정답 초안 오차단을 나눠 비교한다. 부분 실패는 성공 자료 보존과 실패 대상 안내를 함께 검사한다. 현재 평가 파일에 이 지표가 전부 구현됐다고 간주하지 않는다.
- 오류를 주입한 테스트는 오류 주입으로, 실제 모델 답변은 실모델 관찰로 표시한다. 조건이 다른 실행·과거 캡처의 시간 간격을 성능 수치로 합치지 않는다.
